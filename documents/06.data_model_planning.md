# Data Model Planning Worksheet

## **소개**

- 개발에 앞서 애플리케이션의 **데이터 구조를 최대한 체계적으로 정의**하는 것이 이 과제의 목표입니다.
- 엔터티, 필드, 관계, 권한, 비즈니스 규칙 등을 사전에 정리하는 작업은 **데이터 모델링의 오류나 누락을 줄이고**, 이후 개발의 방향성을 명확히 하는 데 큰 도움이 됩니다.
- **어떤 엔터티(데이터 객체)** 들이 존재하며, **서로 어떤 관계와 규칙**을 가지고 있는지를 중심으로 워크시트를 작성해보세요.
- 작성이 어렵다면, 함께 제공되는 예시를 참고하셔도 좋습니다.
- 참고 : [https://gist.github.com/serranoarevalo/fe7bb3affae2e7450c325267d0c48257](https://gist.github.com/serranoarevalo/fe7bb3affae2e7450c325267d0c48257)

## 1. 시스템의 핵심 엔터티(Entities)는 무엇인가요? (3~5개)

*애플리케이션에서 관리할 핵심 객체(주로 데이터베이스 테이블이 될 대상)를 3~5개 나열하세요.*

- Goal (& Habit)
- ActionPlan
- User
- Reward History
- Plan History

---

## 2. 각 엔터티의 필드를 정의하세요

*각 엔터티에 대해 주요 속성과 데이터 타입, 필요한 제약 조건 등을 정의하세요.*

### Goal (& Habit)

- `id` (UUID)
- `title` (string)
- `description` (string)
- `created_at` (timestamp)
- `updated_at` (timestamp)
- `start_date` (date)
- `end_date` (date)
- `owner_id` (UUID)
- `reward` (integer)
- `use_message` (enum: None, once a day, once a week, once a month)
- `status` (enum: Not started, started, failed, Finished)

### Action Plan

- `id` (UUID)
- `title` (string)
- `description` (string)
- `created_at` (timestamp)
- `period` (enum: day, week, month)
- `start_date` (date)
- `end_date` (date)
- `goal_id` (UUID)
- `completed` (boolean)

### User

- `id` (UUID)
- `email` (string)
- `phone` (string)
- `password` (string)
- `first name` (string)
- `last name` (string)
- `role` (enum: User, Admin)
- `status` (enum: active, inactive)
- `last_sign_in` (timestamp)
- `created_at` (timestamp)
- `updated_at` (timestamp)

### Reward History

- `id` (UUID)
- `user id` (UUID)
- `created_at` (timestamp)
- `change` (integer)
- `balance` (integer)

### Plan History

- `id` (UUID)
- `user id` (UUID)
- `started_at` (timestamp)
- `ended_at` (timestamp)
- `type` (enum: monthly, annual)
- `price` (integer)
- `status` (enum: active, inactive)

---

## 3. 어떤 관계들이 존재하나요?

*각 엔터티 간의 관계를 정의하세요 (예: 일대다, 다대다 등). 가능하다면 ERD(엔터티 관계도)를 그려보세요.*

- One User → many Goal & Habit (소유 관계)
- One Goal & Habit → many ActionPlan (소유 관계)
- One User → many Reward history (소유 관계)
- One User → many Plan history (소유 관계)

---

## 4. 어떤 CRUD 작업이 필요한가요?

*각 엔터티에 대해 Create, Read, Update, Delete 중 어떤 작업이 필요한지, 그리고 누가 수행할 수 있는지를 정의하세요.*

| Entity         | Create                         | Read                           | Update                         | Delete               |
| -------------- | ------------------------------ | ------------------------------ | ------------------------------ | -------------------- |
| Goal (& Habit) | ✅ (User / Admin)              | ✅ (작성자 / Admin)           | ✅ (작성자 / Admin)           | ❌ (아카이브만 가능) |
| Action Plan    | ✅ (권한 있는 사용자 / Admin) | ✅ (권한 있는 사용자 / Admin) | ✅ (권한 있는 사용자 / Admin) | ❌ (아카이브만 가능) |
| User           | ✅ (Admin)                     | ✅ (본인 / Admin)              | ✅ (본인 / Admin)              | ❌ (비활성화만 가능) |
| Reward History | ✅ (Admin)                     | ✅ (본인 / Admin)              | ✅ (Admin)                     | ✅ (Admin)           |
| Plan History   | ✅ (Admin)                     | ✅ (본인 / Admin)              | ✅ (본인 / Admin)              | ✅ (Admin)           |

---

## 5. 어떤 규칙이나 제약이 존재하나요?

- User 는 소유한 Goal (& Habit) 에 접근 가능
- User 는 소유한 Action Plan 에 접근 가능
- User 는 소유한 Reward History 에 접근 가능
- User 는 소유한 Plan History 에 접근 가능
